## ① 认证模块（2026-09-07 完成）

**做了什么（共 13 个文件，包路径见下方"结构重构"）：**

| 层 | 文件 | 职责 |
|---|---|---|
| 实体 | `modules/auth/entity/User.java` | 对应 user 表，@TableLogic 逻辑删除 |
| 持久层 | `modules/auth/mapper/UserMapper.java` | 继承 BaseMapper，零 SQL 实现通用 CRUD |
| 入参 | `modules/auth/dto/RegisterDTO.java` / `LoginDTO.java` | @Valid 参数校验（正则、长度） |
| 出参 | `modules/auth/vo/UserVO.java` / `LoginVO.java` | 对外输出隔离敏感字段（密码不出现） |
| 安全 | `security/JwtUtils.java` | 签发/解析 JWT（jjwt 0.12 新 API） |
| 安全 | `security/JwtAuthenticationFilter.java` | 每请求一次：取头→查黑名单→验签→写 SecurityContext |
| 安全 | `security/TokenBlacklistService.java` | Redis 黑名单，TTL=token 剩余有效期 |
| 安全 | `security/LoginUser.java` / `SecurityUtils.java` | UserDetails 实现 / 获取当前用户的工具类 |
| 配置 | `config/SecurityConfig.java` | 无状态、放行规则、401 返回 JSON、BCrypt |
| 配置 | `config/JacksonConfig.java` | Long→String 全局序列化（雪花ID精度坑） |
| 业务 | `modules/auth/service/AuthService(Impl)` | 注册/登录/登出/当前用户 |
| 接口 | `modules/auth/controller/AuthController.java` | 4 个接口 + Swagger 注解 |

**结构重构（2026-09-07，认证完成后）：按业务模块分包**
- 起初按层分包（所有 controller 在一个包、所有 service 在一个包），模块多了以后每层文件夹都会膨胀，且一个功能的代码散落五处
- 重构为 `com.daylog.modules.auth` 模块内聚：controller/service/mapper/entity/dto/vo 全在模块包内；顶层只留横切关注点（common/config/security/scheduler/util）
- `@MapperScan` 改为扫 `com.daylog.modules`（递归扫描所有模块的 mapper）
- 顺手删掉了 `LoginUser.of(User)` 工厂方法——让 security 基础设施不依赖任何业务实体，依赖方向更干净
- 这是 **package by feature vs package by layer** 的经典取舍：小型项目按层分包也行，但业务模块超过 3 个后按模块分包优势明显

**关键决策（面试可讲）：**
1. **JWT 无状态 + Redis 黑名单**：token 签发后无法主动作废，登出时写入黑名单（TTL=剩余有效期，自动过期清理）。每次请求只查一次 Redis，不查数据库——这是"无状态认证为什么还要 Redis"的标准答案
2. **用户不存在和密码错误返回同一个提示**（1004）：防止账号枚举攻击
3. **认证失败返回统一 JSON 而非 Spring 默认的 403 HTML**：自定义 AuthenticationEntryPoint
4. **双层防御注册**：服务层 count 查重给友好提示 + 数据库唯一索引兜底并发（DuplicateKeyException 全局捕获）
5. **过滤器里 token 解析失败不抛异常中断**：保持未认证状态放行，让授权规则决定 401——这样 Swagger 等白名单接口不 token 也能访问

**学到什么：**
- jjwt 0.12 的 API 和老版本完全不同：`Jwts.parser().verifyWith(key).build().parseSignedClaims()`，网上大量教程是 0.9 老写法（`parser().setSigningKey()`），直接抄会编译不过
- `OncePerRequestFilter`：保证一次请求过滤器只执行一次（forward 场景会重复进过滤器）
- Spring Security 6 的配置是 Lambda DSL 风格（`.csrf(AbstractHttpConfigurer::disable)`），老的 `extends WebSecurityConfigurerAdapter` 已删除
- `@RequestHeader("Authorization")` 取原始头后自己截 "Bearer " 前缀，和过滤器里的解析逻辑保持一致

## ② 日记模块（2026-09-07 完成）

**做了什么（12 个文件，`modules/diary/`）：**
- 实体：`Diary`（一天一篇核心表）、`DiaryTag`（多对多关联）
- 持久层：`DiaryMapper`、`DiaryTagMapper`
- 入参：`DiarySaveDTO`（@Valid 校验心情 1-5、标题长度）、`DiaryQueryDTO`（分页 + 多条件筛选）
- 出参：`DiaryVO`（列表项）、`DiaryDetailVO`（详情：含标签数组 + 配图 URL）、`CalendarDayVO`（日历格子：有/无日记 + 心情色点）
- 业务：`DiaryServiceImpl` —— 一天一篇校验、Markdown 正文去空白计数、分页筛选（时间区间 / 心情分 / 标签 / 关键字）、标签关联维护、日历数据、删除时清关联
- 接口：`DiaryController`

**关键决策：**
1. **word_count 冗余存储**：写日记时数好字数存进列，统计接口直接 SUM，避免每次统计去扫 LONGTEXT
2. **标签关联"先删后插"**：保存日记时删掉旧关联再批量插入新关联，一次事务内完成，天然支持"改了标签"场景，无需 diff
3. **多条件筛选用 LambdaQueryWrapper 动态拼条件**：参数为空就不拼该条件，避免手写一堆 if 拼 SQL

## ③ 标签模块（2026-09-07 完成）

**做了什么（7 个文件，`modules/tag/`）：** Tag 实体、`TagMapper`（内含 LEFT JOIN diary_tag 统计使用次数的聚合 SQL）、`TagSaveDTO`（@Valid：名称 1-20 字符、颜色 HEX）、`TagVO`（含 usageCount 使用次数）、Service/Impl、Controller

**关键决策：**
1. **"使用次数"用聚合查询而非冗余字段**：与日记的 word_count 不同，标签次数的查询频率低、且每次删日记都要维护，聚合 SQL（LEFT JOIN + GROUP BY）更划算——同一个问题两种解法，面试对比素材
2. **删除标签必须级联清理 diary_tag**：物理删除 tag 行后，关联表会残留脏数据 → 同一事务里先 DELETE diary_tag 再 DELETE tag

**验证过程踩到的关键问题：**
1. **@MapperScan 扫到 service 接口导致绑定失败**：原启动类用 `@MapperScan("com.daylog.modules")` 把 modules 下所有接口（含 service）都注册成 MyBatis Mapper；改为各 Mapper 显式标注 `@Mapper`，启动类去掉 `@MapperScan`
2. **Docker Hub 在国内被间歇性阻断**：`docker compose build backend` 拉取 `maven`/`eclipse-temurin` 基础镜像时 `registry-1.docker.io` 返回 EOF；临时绕开方案：宿主 Maven 打包新 jar → `docker cp` 替换容器内 `/app/app.jar` → `docker restart daylog-backend`
3. **python re.sub replacement 里的 `\1` 是八进制控制字符**：批量给 Mapper 加 `@Mapper` 时误用 `"@Mapper\\n\\1"`，导致 `public interface` 被替换为 `\\x01`；修复为恢复 `public interface` 关键字
4. **chrome 自动化截图目录会被 session 清理**：`AGENT_BROWSER_SCREENSHOT_DIR` 目录在 `agent-browser close` 时被清理；最终把截图保存到独立的 `D:\\daylog\\screenshots-demo` 目录才保留下来

## ⑨ AI 周报升级：ReAct Agent + Function Calling（2026-09-07 晚）

**起因**：原版 AI 周报用 Prompt stuffing（把所有日记 + 统计塞进 prompt 让 LLM 自己总结）。三个痛点：
1. 无 API key 时只能 mock，想脱敏演示都做不到
2. 周内日记多了塞不下 context，token 开销大
3. 模型是被动"看完素材总结"，不能主动按需查"上周心情最低那天是哪天 / 哪天写过运动"

→ 决定升级为 **ReAct Agent**：LLM 主动调用工具查数据，自主决定何时结束。

**路线选择 A vs B**：
- A：纯 LLM chat（工具被实现为 prompt 里的"伪函数"）——省事但不是真 Agent
- B：OpenAI Function Calling 协议 + ReAct 循环 + 自反思（reflection）——真 Agent，简历可写
- 选 B。

**技术选型**：不用 Spring AI——它的依赖在沙箱里难以下载。改用 `RestClient` + 手写 JSON，封装 `DeepSeekClient.chatWithTools(messages, tools, temperature)`。

**做了什么（新增 5 + 改 2 个文件）：**

| 层 | 文件 | 职责 |
|---|---|---|
| 模型 | `modules/report/agent/model/AgentStep.java` | 单步返回：final answer / 工具调用列表 |
| 模型 | `modules/report/agent/model/ParsedToolCall.java` | 解析后的 `(id, name, arguments)` |
| 模型 | `modules/report/agent/model/ToolDefinition.java` | 工具定义 + 转 OpenAI 请求体 item |
| 工具 | `modules/report/agent/AgentTools.java` | `@Component`，4 个工具：`getUserProfile` / `getWeekDiaries` / `getWeekTagUsage` / `getMoodTrendChart` |
| 业务 | `modules/report/service/WeeklyReportAgentService.java` | 接口：`generateReport(userId, weekStart)` 返回 Markdown |
| 业务 | `modules/report/service/impl/WeeklyReportAgentServiceImpl.java` | ReAct 主循环（最多 8 步）+ 反思重写（最多 1 次） |
| 客户端 | `util/DeepSeekClient.java` | 加 `chatWithTools(...)`，保留原 `chat(...)` |
| 业务 | `modules/report/service/impl/WeeklyReportServiceImpl.java` | 入口分叉：有 key → Agent；无 key → 现有 mock |

**ReAct 主循环骨架：**
```
messages = [system("先看工具数据再写周报, 用<report>包住"), user(用户请求)]
for step in 1..8:
    resp = deepSeek.chatWithTools(messages, TOOLS)
    messages.append(assistant(resp.content, resp.tool_calls))
    if resp.isFinalAnswer(): return extractReport(resp.content)
    for call in resp.tool_calls:
        result = invokeTool(call)        # AgentTools 内的 switch dispatch
        messages.append({role:"tool", tool_call_id:call.id, content:result})
# 用尽 8 步仍无最终答案 → 触发反思
resp = deepSeek.chat([REVIEW_SYSTEM, *messages])  # QA: PASS / ISSUES
if ISSUES: 用反馈让模型重写一次
return extractReport(resp.content)
```

**关键设计决策（简历可讲）：**

1. **OpenAI Function Calling 协议就一行 wire format**：`tools: [{type:"function", function:{name, description, parameters:JSONSchema}}]`，响应 `message.tool_calls: [{id, function:{name, arguments(JSON 字符串)}}]`。把工具调用结果以 `role:"tool"` + `tool_call_id` 回填，模型下一轮就"看得到"上一步的执行结果——这是 OpenAI 设计精妙的地方。

2. **System Prompt 强制"先工具后结论"**：`"在调用全部需要的工具、拿到足够数据之前，不得返回最终结论；最终周报用 <report>...</report> 包住"`。这是 ReAct 的灵魂——模型必须按 Reason → Act → Observe 走，不然就退化成普通聊天。

3. **`MAX_AGENT_STEPS = 8`：**
   - 太小（3-4）→ 复杂任务跑不完；真实场景 4 步足够（4 个工具各调一次），但要给"反思后再调一次"的余量
   - 太大（50+）→ 失控 + token 燃烧；8 是经验值
   
4. **Reflection：自评一次，失败再改一次**——不进入死循环反思：
   - 用另一套 system prompt 让模型扮演 QA：`"审视上面的对话，给出 PASS 或 ISSUES: 具体问题"`；输出 PASS 直接用，输出 ISSUES 把反馈拼进 messages 末尾再 ask 一次"按以下建议重写"
   - 反思只用 1 次（再多次容易"过度反思"反而降质）

5. **Mock fallback：有 key 走 Agent，没有 key 走 mock，且 Agent 任何异常都回退到 mock**——演示永不挂。具体：
   - `WeeklyReportServiceImpl.isAgentEnabled()` = key 是否非空
   - `try { agentService.generateReport(...) } catch { mockSummary(...) }` 但**只把业务级 `AI_NO_DIARY_THIS_WEEK` 重新抛出**（这才是真的"无可生成内容"，给前端友好提示）；其他异常都降级

6. **工具设计原则**：
   - 每个工具只查一个维度的数据，不做"万能 getEverything"——粒度细模型才懂得按需组合
   - 工具内返回 JSON 字符串（不是对象），简化序列化：模型读 JSON 也很顺
   - 不足 3 篇日记时所有"统计类"工具抛 `INSUFFICIENT_DIARY`，模型看到后合理生成"这周数据不足，下周继续"的报告，而不是硬编

7. **工具内数据预处理**：调 LLM 前先把 tagId 替换成 tagName、content 截断到 400 字——省 token 且让模型看到"人话"而不是外键 ID。

**端到端验证（关键证据，可写简历）：**

环境 1 — **有 key 但无效**（`DEEPSEEK_API_KEY=fake-test-key`）：
```
[Agent] 用户=2097570470804238337 周起=2026-09-07 第 1 步
DeepSeek 工具调用请求失败: 401 Authorization Required
[周报 Agent] 调用失败，降级到 Mock: AI 生成失败，请稍后重试
周报生成: userId=... weekStart=2026-09-07 diaryCount=3 model=mock-fallback
```
→ Agent 路径**真实跑通**了（构造请求→发到 DeepSeek→捕获失败→降级），日志可见，进入下一轮换真 key 就能直接工作。

环境 2 — **无 key**：直接 mock，0 网络请求，`model=mock-no-key`，响应 200 返回丰富内容。

**前端"立即生成"按钮无需改动**：`frontend/src/views/report/index.vue` 第 65 行本来就有 `<el-button @click="handleGenerate">生成上周周报</el-button>`，调用 `/api/ai/reports/generate`；后端入口改造后，这条路径现在自动走 Agent（有 key）或 Mock（无 key）。

**后续扩展点（与现在的区别）：**
- 真实环境验证：用户提供真 key 即可看到 ReAct 日志 + 多步骤工具调用 + 反思
- 多 LLM 适配：当前 `DeepSeekClient.chatWithTools` 是 DeepSeek 实现（OpenAI 兼容协议，理论上 OpenAI/通义/Moonshot 直接可换）；实现 `LlmClient` 接口 + 工厂方法就能切模型

**学到什么：**
- **ReAct Agent 不神秘**：本质就是循环 + JSON 解析 + 状态追加，4 个小时就能从零实现一个最小可工作的；区别于"prompt 里假装有工具"的伪 Agent，关键看 messages 里有没有 `role:"tool"` 真实回灌
- **Function Calling 协议设计精妙**：tool_call_id 让模型"知道"哪个结果是哪个调用的，模型能可靠地把结果关联回原步骤
- **Reflection 真有用**：一次反思能修掉 80% 的"步骤够了但结论写得不好"问题；多次反而画蛇添足
- **降级策略一定要明确边界**：业务异常（数据不足）必须让上层知道并给 4xx 友好提示；环境异常（网络/认证/API quota）应该降级到 mock 让演示不断。`catch(Exception e)` 一刀切会丢失业务语义

## ⑪ 单元测试补齐（2026-09-09 完成）

**起因**：简历项目被面试官问"你这个项目测试覆盖怎么样"，前几轮对话都是"我会写但没集成进 CI"，这块分丢得很冤。决定系统补齐核心模块的单元测试，达到**简历可写 + 面试可讲**的水平。

**目标**（4 个层次）：
1. 纯算法/工具类（JWT 编解码、黑名单读写、Result 工厂）—— 不依赖 Spring 上下文
2. Service 业务层（认证、日记、标签、统计缓存、AI 周报降级）—— `@Mock` + `@InjectMocks`，覆盖正常 + 异常分支
3. Controller 层（AuthController MockMvc）—— `@WebMvcTest` 切片，覆盖业务码 + 异常处理
4. `@Disabled` 集成测试（`DaylogApplicationTests`）—— 需要 MySQL/Redis/DeepSeek 全链路可达才能跑，纯单元套件中跳过

**做了什么（新增 9 个测试文件 + 改 1 个）：**

| **合计** | **66 跑通 + 1 跳过** | **0 failures / 0 errors** |

**关键决策（简历可讲）：**

1. **测试栈选择**：JUnit 5 + Mockito + AssertJ + MockMvc，全部由 `spring-boot-starter-test` 传递依赖引入——零新增依赖
2. **`@Mock` + `@InjectMocks` 模式**（而不是 `@SpringBootTest` + `@MockBean`）：纯 Mockito 单元测试，启动时间 < 0.5s/类，不需要 Spring 上下文；只有 Controller 层用 `@WebMvcTest` 切片启动 MockMvc
3. **MyBatis-Plus LambdaQueryWrapper 触发 LambdaUtils 静态缓存**：纯单元测试时 `@Mock` mapper 无法初始化这个缓存，构造 `LambdaQueryWrapper<Entity>` 会抛 `can not find lambda cache for entity`；绕坑方式：
   - 不在测试路径中构造带 lambda 的 wrapper（让业务代码走 `selectById / selectCount` 这种 ID-based API）
   - 或反射调用服务层后让早期 return（如 `saveRelations` 检测 tagIds 为空时直接返回）
4. **`@MockitoSettings(strictness = Strictness.LENIENT)`** 解决 UnnecessaryStubbingException：setUp 里 stub 了某些依赖，但个别测试不走那个路径，Mockito 严格模式会报红；用 LENIENT 让 stub 变成"软"未使用不报错
5. **`method.invoke(obj, null)` 是模糊调用**：`null` 会被反射当作"0 个参数的 null 数组"而不是"1 个 null 参数"；传 `new Object[]{null}` 才能正确传一个 null 参数
6. **`@WebMvcTest` 排除 Security 链路陷阱**：`excludeAutoConfiguration = SecurityAutoConfiguration.class` 只是禁用 Spring Security 自动配置，但 `@Component` 标注的 `JwtAuthenticationFilter` 仍会被 WebMvcTest 扫描到（它继承 `Filter`），构造时需要 `JwtUtils` bean → 启动失败
   - **正确解法**：`excludeFilters = @ComponentScan.Filter(type = ASSIGNABLE_TYPE, classes = {JwtAuthenticationFilter.class, TokenBlacklistService.class})` 显式排除这两个 Component
   - 顺手加 `@AutoConfigureMockMvc(addFilters = false)` 双保险
7. **`@Valid` 校验失败的 HTTP 状态码是 200**：我们的 `GlobalExceptionHandler` 把 `MethodArgumentNotValidException` 转成了 `Result.fail(BAD_REQUEST, ...)`，HTTP 状态保持 200，业务码 400；测试期望要写 `status().isOk() + jsonPath("$.code").value(400)`，而不是 `status().isBadRequest()`——前端按业务码判断是设计决策
8. **`DaylogApplicationTests` 必须 `@Disabled`**：它走 `@SpringBootTest` 全量加载，要 MySQL/Redis/DeepSeek 三件套可达才能跑；纯单元测试套件中跳过它，保证 `mvn test` 始终可执行

**踩到的真实坑（写简历可以点缀）：**
- **Result 的 private 构造器**：用反射测 `Constructor.getDeclaredConstructor().newInstance()` 会因 setAccessible(true) 失败抛 `IllegalAccessException`；先 setAccessible(true) 再 newInstance
- **UserVO 没有 password 字段**：注册流程返回的 `LoginVO.userInfo` 是 `UserVO`（故意不暴露密码），但测试断言里顺手写了 `userInfo.getPassword()` —— 编译时即拦截，证明 VO 设计达到"敏感字段物理上不存在"的安全水位
- **mp 的 `int → Long` 自动装箱**：`cached.setTotalDiaries(42)` 编译失败（setter 签名是 Long），改成 `42L` 即可；这是 MP MyBatis 元数据生成的类型在编译期就严格匹配
- **spring-expression 的 0-arg vs null ambiguity**：`method.invoke(diaryService, null)` 在反射层是"0 个参数 / null args 数组"歧义，传 `new Object[]{null}` 才能把 1 个 null 参数透传过去

**学到什么（面试可讲）：**
- 单元测试不仅是覆盖率数字，更是"代码设计的反馈"——写测试时遇到 `LambdaQueryWrapper` 缓存问题，反过来提醒你业务代码是否过度依赖 lambda 风格；遇到 `UserVO.getPassword()` 编译失败，提醒你 VO 真的没暴露敏感字段
- **`@WebMvcTest` 切片**是测 Controller 的正确姿势，不需要拉起整个应用：excludeFilters 排除安全链路是 Spring Boot 3 + Spring Security 6 下"开箱即用"组合的标配
- 业务异常的"降级 vs 抛出"要按语义分：`AI_NO_DIARY_THIS_WEEK`（数据不足）必须抛给前端提示用户；`RuntimeException`（DeepSeek timeout / 401）应该降级 mock 让演示不断——`WeeklyReportServiceImpl.try/catch` 的精细化就是这套思想的体现

## 1. 本机命令行 Maven 损坏（环境问题，2026-09-06）

**现象**：命令行执行 `mvn -version` 报错 `ClassNotFoundException: org.codehaus.plexus.classworlds.launcher.Launcher`

**原因**：Maven 安装目录或环境变量（MAVEN_HOME / M2_HOME）损坏，找不到 Maven 核心类。

**解决**：不修了——IDEA 自带捆绑 Maven，在 IDEA 里开发构建完全不受影响。若以后想修：重新下载 Maven 解压后重配环境变量即可。

## 2. Vite 官方模板自带文件需要清理（2026-09-06）

**现象**：`npm create vite` 创建的工程里有 HelloWorld.vue、style.css、vue.svg 等示例文件。

**解决**：删除示例文件，改为自己的规范结构（src/api、src/router、src/stores...），全局样式收敛到 `src/assets/styles/index.css`。教训：脚手架给的只是起点，目录结构要按项目规范重新组织。

## 3. Element Plus 全量引入导致构建产物过大（2026-09-06）

**现象**：`npm run build` 警告 chunk 超过 500KB，主包约 1MB。

**原因**：main.js 里 `app.use(ElementPlus)` 全量引入了所有组件。

**现状**：先保持全量引入（开发期简单可靠），功能完成后再做**按需引入优化**（unplugin-vue-components + unplugin-auto-import），作为性能优化的一项——这本身就是简历上"构建产物优化"的素材。

## 4. JS 处理 Long 型雪花 ID 会丢精度（已防御，2026-09-07 落地）

**现象（会出现的）**：后端返回的雪花 ID（19 位 Long）在前端显示成错误值，末几位变 0。

**原因**：JS 的 Number 只有 53 位安全整数，装不下 64 位 Long。

**解决（已实施）**：`config/JacksonConfig.java` 注册 `ToStringSerializer`，全局把 Long 序列化为 String。验证方法：调用 `/auth/register`，返回的 userId 应是带引号的字符串 `"1948..."` 而非数字。这是所有用雪花 ID 的前后端分离项目的必踩坑。

## 5. 预防：jjwt 0.12 的新 API 与网上老教程不兼容（2026-09-07）

**现象（会出现的）**：照网上教程抄 JWT 代码，出现 `parser().setSigningKey(...)` 找不到方法、`SignatureAlgorithm` 类不存在等编译错误。

**原因**：jjwt 0.11/0.12 大改了 API，而大量博客还是 0.9 老写法。本项目用的 0.12.6 正确写法：
- 签发：`Jwts.builder().subject(...).signWith(key).compact()`
- 解析：`Jwts.parser().verifyWith(key).build().parseSignedClaims(token).getPayload()`
- 密钥：`Keys.hmacShaKeyFor(bytes)`（HS256 要求至少 32 字节）

**教训**：抄代码先看依赖版本号，日期久远的 JWT 教程基本都过时了。

## 6. 预防：@Component 的过滤器会被注册两次（2026-09-07）

**现象（会出现的）**：JWT 过滤器里的日志一条请求打印两次，或断点进两次。

**原因**：过滤器类标 `@Component` 后，Spring Boot 自动把它注册进 Servlet 容器全局过滤器链；SecurityConfig 里 `addFilterBefore` 又注册一次 → 执行两遍。

**解决（已实施）**：SecurityConfig 里声明 `FilterRegistrationBean` 并 `setEnabled(false)`，关闭自动注册，只保留 Security 链里那一份。

## 7. npm run build 偶发 502 Client network socket disconnected（环境问题，2026-09-07）

**现象**：`npm run build` 执行中断，报 `502 Client network socket disconnected` 或 `copilot.tencent.com` 代理相关错误。

**原因**：构建工具经网络代理拉取依赖/上报时连接被代理断开（网络抖动），不是代码问题。

**解决**：重跑一次即可；依赖已缓存在 node_modules / npm 缓存，第二次通常秒过。判断标准：输出出现 `✓ built in xxx` 即成功，chunk 体积警告（>500KB）不是错误。

## 8. 本地 dev 配置硬编码 localhost，无法直接容器化（2026-09-07）

**现象**：写 Dockerfile 时发现 `application-dev.yml` 的数据库地址写死 `localhost:3306`——容器里 localhost 是容器自己，连不上宿主机。

**原因**：dev 配置只面向"IDEA 本地跑"，Docker 环境需要能通过环境变量注入的连接串。

**解决**：新增 `application-prod.yml`，所有连接参数写成 `${DB_HOST:mysql}` 这类"环境变量 + 默认值"形式；compose 里设 `SPRING_PROFILES_ACTIVE=prod` 并在 environment 注入 DB_HOST=mysql（服务名）。**经验：容器化不是加个 Dockerfile 就行，配置必须与环境解耦。**

## 9. Nginx 部署 SPA 要同时处理三个 location（2026-09-07）

**现象（如果漏配会出现的）**：前端页面 404 / 接口 404 / 图片裂图。

**原因与解决**（Vue history 路由 + /api 前缀 + /files 图片，缺一不可）：
1. `location /` 加 `try_files $uri $uri/ /index.html`——否则刷新 `/diary/xxx` 直接 404（history 模式无服务器路由文件）
2. `location /api/` + `proxy_pass http://backend:8080/`——末尾的 `/` 会把 `/api` 前缀剥掉转发（`/api/diary` → `/diary`），忘加 `/` 会带前缀打到后端导致 404
3. `location /files/` 反代到后端——附件 URL 是后端返回的相对路径 `/files/...`，浏览器请求落到 Nginx，必须回源后端磁盘目录；否则图片 404

## 10. docker-entrypoint-initdb.d 只首次执行（2026-09-07）

**现象（会出现的）**：改了 schema.sql 重启容器发现表结构没变。

**原因**：MySQL 官方镜像只在**数据卷为空**（首次启动）时执行 `/docker-entrypoint-initdb.d/` 下的脚本，之后挂载的持久卷里有数据就不再执行。

**解决**：首次启动就把 schema.sql 挂进去；之后改表结构要手动进容器执行 SQL（`docker exec -i daylog-mysql mysql -uroot -p < schema.sql`），或删除卷 `docker compose down -v` 重置（会清数据，慎用）。

## 11. Git Bash 里跑 Maven 报 classworlds Launcher 找不到（环境问题，2026-09-07）

**现象**：`mvn -version` 报 `ClassNotFoundException: org.codehaus.plexus.classworlds.launcher.Launcher`，换 IDEA 内置 Maven 也一样。看起来像 Maven 安装损坏。

**原因**：不是 Maven 坏了——是 **git bash 的路径问题**。`mvn` 是 sh 脚本，它把 `MAVEN_HOME` 拼成 Unix 风格路径（`/d/softwareDownload/...`）直接传给 Windows 原生 `java.exe`；java 不认 `/d/...` 格式，加载不到 boot 下的 classworlds jar。

**解决**（绕开 mvn 脚本，直接调 java + classworlds）：
```bash
java -classpath "$(cygpath -w $MAVEN_HOME/boot/plexus-classworlds-*.jar)" \
     "-Dclassworlds.conf=$(cygpath -w $MAVEN_HOME/bin/m2.conf)" \
     "-Dmaven.home=$(cygpath -w $MAVEN_HOME)" \
     org.codehaus.plexus.classworlds.launcher.Launcher -version
```
在 git bash / 沙箱终端里跑 Maven 都可用这招；正常终端（cmd / IDEA）直接用 `mvn` 即可。

## 13. @MapperScan 包级扫描误注册 service 接口（2026-09-07）

**现象**：`@MapperScan("com.daylog.modules")` 递归扫描时，把 auth/diary/... 各模块下的 **service 接口也注册成了 Mapper 代理**，运行时启动报 `Invalid bound statement: AuthService.register`（找不到 XML/语句）。

**原因**：`@MapperScan` 是包扫描，包里的**所有接口**都会被当作 Mapper 尝试创建代理对象（不要求接口上有 @Mapper 注解）。

**解决**：去掉包级 `@MapperScan`，改在**每个 Mapper 接口上显式加 `@Mapper` 注解**（数量有限、显式可控）。Spring Boot 靠 `@Mapper` 逐个注册，service 接口不会被误扫。

**补充教训（脚本坑）**：当时用 python 脚本批量给 6 个文件补 `@Mapper`，`re.sub("...", "@Mapper\n\1", ...)` 里的 `"\1"` 被 python 解析为**八进制转义 `\x01` 控制字符**，把 `public interface` 关键字吃掉 → 编译报 `illegal character: '\u0001'`。修复：`data.replace(b'\x01 ', b'public interface ')`。**写正则替换时优先用 `\g<1>`/`\1` 前加 r 前缀，或干脆用 lambda 回调**。

## 14. Docker Hub 网络不可达 → 容器内 jar 热替换（2026-09-07）

**现象**：`docker compose build` 拉 `maven:3.9-eclipse-temurin-17`、`nginx` 等基础镜像时 `registry-1.docker.io` EOF 超时（国内网络），本地又无缓存，**无法重建镜像**。

**解决**（只改 jar 不重建镜像的替代方案）：
1. 宿主机用 Maven 打出新 jar（backend/target/daylog-backend.jar）
2. `docker cp backend/target/daylog-backend.jar <backend容器>:/app/daylog-backend.jar` 覆盖
3. `docker restart <backend容器>`
适用后端改动不需要新增依赖/改 Dockerfile 的场景；新增依赖或要换 nginx 配置时仍需解决镜像拉取。

## 15. agent-browser 截图三坑（2026-09-07）

1. **screenshot 参数语法**：`screenshot "" "绝对路径.png"` —— 第一个空参数是"元素选择器"，第二个才是保存路径；只传一个相对文件名会被当成元素 selector，导致自动命名乱飞（产生 04-diary-edit.png / 05-calendar.png 之类非预期文件）。
2. **ref 会过期**：每次 snapshot 后 ref 编号才有效；路由跳转/截图之后必须重新 snapshot 再 click，否则 `Unknown ref` 或**点错元素跳到别的页面**。
3. **daemon 偶发拒绝连接**：`Could not configure browser ... (os error 10061)`，多为上一个命令还占着 daemon，重试即可。
4. **长页面截图建议 sleep 2~3s 等 ECharts 渲染完再截**，否则图表是空 canvas。

## 16. Element Plus 按需引入的两个隐藏坑：指令与函数式组件（2026-09-07）

用 `unplugin-auto-import` + `unplugin-vue-components` + `ElementPlusResolver` 做按需引入后，**页面能渲染但两样东西会静默失效**，构建不报错、控制台可能也不报：

1. **`v-loading` 等指令**：unplugin 只处理**模板组件**和 **import 的 API**，不处理指令。5 个页面用了 `v-loading`，必须在 main.js 手动 `import { ElLoading } from 'element-plus'` + `app.use(ElLoading)`，同时手动引入 `element-plus/es/components/loading/style/css`
2. **ElMessage / ElMessageBox 样式**：这两个是**函数式组件**（不是模板组件），代码里 `import { ElMessage } from 'element-plus'` 是显式导入，unplugin 不会给显式导入注入样式 → 消息能弹出来但**没有样式/位置错乱**。解法：main.js 手动 import `element-plus/es/components/message/style/css` 和 `message-box/style/css`

**规律总结**：按需引入 = "模板组件自动、其余手动"。凡是绕过模板编译机制的东西（指令、函数式调用、`app.use` 全局插件），样式和注册都要自己补。

## 17. ECharts 按需注册少引组件不报错，图表就是空白（2026-09-07）

`import * as echarts from 'echarts'` 改成 `echarts/core` + `echarts.use([...])` 后，**漏注册哪个组件，对应功能就静默失效**——控制台无报错，canvas 渲染出来但内容空缺：

- 漏 `CalendarComponent` → 热力图的日历坐标系不画（series type=heatmap + coordinateSystem=calendar 需要两个模块）
- 漏 `VisualMapComponent` → visualMap 配置被忽略
- 漏 `GridComponent` → 折线图的 grid/xAxis/yAxis 全失效

**排查方法**：对照 setOption 里用到的每个配置项（title/tooltip/legend/grid/visualMap/calendar/axis）逐个检查是否在 `echarts.use()` 里注册了对应 `XxxComponent`。stats 页最终需要：LineChart/PieChart/HeatmapChart + Title/Tooltip/Grid/Legend/VisualMap/Calendar + CanvasRenderer，共 10 个模块，stats chunk 从 1.1MB 降到 581KB。

## 18. agent-browser 点击视口外的元素"成功"但实际无效（2026-09-08）

**现象**：日记详情页底部的"编辑"按钮，`click @ref` 返回 `✓ Done`，但页面没跳转、URL 不变、控制台无报错——看起来像路由没生效，其实是**点击根本没落在按钮上**。

**原因**：按钮在长 Markdown 正文下方的折叠区，agent-browser 点击前未自动滚动到元素位置，坐标落在了别处。

**解决**：点击视口外元素前先 `scrollintoview @ref`，再 `click @ref`。

**教训**：自动化测试里"命令成功"≠"点击生效"，涉及折叠区元素时要用 URL/snapshot 二次确认，别急着怀疑业务代码。

## 19. agent-browser 在移动 H5 验证里的三个新坑（2026-09-08）

**现象**：用 agent-browser 验证 `new_frontend` 移动前端时，多次遇到"命令成功但页面没反应"。

**原因与解决：**
1. **viewport 要用 `set viewport w h` 而不是 open 的 flag**：`agent-browser open --viewport 393x852` 会被阻塞或忽略，正确做法是先 `agent-browser set viewport 393 852`，再 `agent-browser open <url>`。
2. **Vite dev server 初次打开页面 CSS 没加载完，截图空白**：Vite 开发模式下样式是 JS 注入的，open 后立刻 screenshot 会得到空白页，需要 `sleep 2s` 再截。
3. **Vant 按钮的 `@click` 用 agent-browser `click <selector>` 点不到**：`van-button` 内部不是原生的 `<button>`，直接点外层 div 不触发 Vue 事件；最稳的是给按钮加自定义 class，然后 `document.querySelector('.save-btn').click()`。

**经验**：移动端验证不要完全依赖自动化点击，核心流程可用 JS 直接调 API + location.href 导航来验收；截图验收时一定等样式注入完成。

## 20. 容器 ENTRYPOINT 锁死 jar 命名 → docker cp 必须 cp 到 `/app/app.jar`（2026-09-07）

**现象**：想把新构建的 jar 通过 `docker cp backend.jar daylog-backend:/app/backend.jar` 热替换，重启容器后跑的还是旧代码。

**原因**：Dockerfile 里 `ENTRYPOINT ["java", "-jar", "/app/app.jar"]`——路径是硬编码的。无论 cp 进去的文件叫什么名字，容器启动都会去找 `/app/app.jar`，找不到就回退跑镜像里那个旧 jar（或者空目录报错）。

**解决**：cp 永远指向固定路径：
```bash
docker cp D:\daylog\backend\target\daylog-backend-1.0.0-SNAPSHOT.jar daylog-backend:/app/app.jar
docker restart daylog-backend
```
ENTRYPOINT 固定的容器，热替换路径 = ENTRYPOINT 里的路径，别自创别名。

## 21. JWT secret 长度一变 → 算法从 HS256 切到 HS512，旧 token 全失效（2026-09-07）

**现象**：更新 `.env` 时微调了 JWT secret（多了/少了几位），重启后所有用户接口变 401"令牌过期"，即使登录拿到的新 token 也立即 401。

**原因**：jjwt 0.12 的 `Keys.hmacShaKeyFor(bytes)` 根据密钥长度自动选择算法：
- 32 ≤ len < 64 字节 → **HS256**
- ≥ 64 字节 → **HS512**

重启容器后，新签发 token 用 HS512 签；老 token 用 HS256 签（且签名里的 alg 字段明确写了 HS256）。校验时按 alg 选算法，密钥和算法对不上 → 校验失败。

**解决**：固定 secret 长度（如 `openssl rand -base64 48 | head -c 64` 生成固定 64 字节），改 secret 时强制走"全量重登"流程，或把 secret 拆分到 jwt 配置类里固定声明 key length。

**教训**：开发期避免改 secret；改 secret 一定要给用户提示"请重新登录"。

## 22. BusinessException 不能一刀 catch-all re-throw：业务级 vs 环境异常要分开处理（2026-09-07）

**现象**：AI 周报 Agent 路径上线后首次跑，用户配置了 fake-test-key，调用 DeepSeek 401 返回，业务本意是"密钥错了就降级到 mock 让演示能继续"，但前端看到的还是 1004 AI_GENERATE_FAILED，不是 mock 内容。

**原因**：原 `WeeklyReportServiceImpl` 里的降级逻辑写的是：
```java
try { agentService.generateReport(...); }
catch (BusinessException be) { throw be; }   // 一刀切把业务异常全部上抛
catch (Exception e) { return mockSummary(...); }
```
其中"日记不足 3 篇"也抛 `BusinessException(AI_NO_DIARY_THIS_WEEK)`（这是业务异常，应该 4xx 友好提示），而"DeepSeek 401"也是 `BusinessException(AI_GENERATE_FAILED)`（这是环境异常，应该降级）。一刀 re-throw 把后者也吞回给前端，前端一直拿到错误码。

**解决**：按 ResultCode 精确分流：
```java
try { agentService.generateReport(...); }
catch (BusinessException be) {
    if (be.getCode() == ResultCode.AI_NO_DIARY_THIS_WEEK) throw be;  // 真正的业务异常
    log.warn("[周报 Agent] 调用失败，降级到 Mock: {}", be.getMessage());
    return mockSummary(...);                                          // 环境/工程异常 → 降级
}
catch (Exception e) { return mockSummary(...); }
```

**教训**：业务异常 ≠ 工程异常。框架/外部 API 异常应该降级或重试，业务规则异常（如数据不足、参数非法）必须如实上抛给前端。比较稳的做法是给"可降级异常"建一个专门的 `RecoverableException` 子类，catch 它就降级，其他一律上抛——避免每次都要查 ResultCode 魔法值。

## 23. Maven 沙箱不允许读 `C:\Users\陈福樵\.m2\repository` → 用 `-Dmaven.repo.local` 指工作区本地仓库（2026-09-07）

**现象**：在沙箱终端里跑 `mvn package`（即使是绕坑后的 classworlds 直启），会卡在读 `~/.m2/repository/org/springframework/boot/...` 时报 `AccessDeniedException`，因为沙箱对用户目录有 ACL 限制。

**原因**：Maven 默认走 `~/.m2/repository`，而这个目录在沙箱里被禁止读取/写入。

**解决**：提前在工作区里建一个本地仓库缓存目录，每次构建传参指定：
```bash
-Dmaven.repo.local='D:\daylog\.m2\repository'
```
沙箱只对这个工作区路径有完全权限，依赖会先尝试从这里找、没有再走阿里云镜像下载；首次构建慢一点（要下几十 MB），后续增量构建秒过。

**配套**：用 `.mvn-settings.xml`（项目根目录里那份阿里云镜像配置）替代 `~/.m2/settings.xml`——沙箱禁止写用户目录，但工作区里随便写。这个 settings 文件留作模板，给真实 ~/.m2 用，或在 IDEA 里 `Settings → Build → Maven → User Settings` 里手动指过去。

## 24. git bash 跑 curl POST 中文字符串 → Jackson 解码后变乱码（2026-09-07）

**现象**：`curl -X POST -H "Content-Type: application/json" -d '{"title":"今天学 React"}' http://localhost/api/...` 报 400，后端日志说 `JSON parse error: Unexpected end-of-input`，但内容看着没错。

**原因**：git bash 默认字符编码是 UTF-8 但 `curl -d` 直接传字符串，**没有显式以文件或 stdin 形式给出**时，git bash 会按系统 codepage 把中文字符转成 GBK 再编码进请求体；后端 Jackson 默认按 UTF-8 解 → 一个 GBK 字节流被当 UTF-8 解码，部分多字节字符截断，剩下的就是乱码 + 提前结束的 JSON。

**解决（三种，推荐第一种）**：
1. **写文件再 `--data-binary @file.json`**：
   ```bash
   cat > req.json <<'EOF'
   {"title":"今天学 React","content":"...","mood":5}
   EOF
   curl -X POST -H "Content-Type: application/json; charset=utf-8" \
        --data-binary @req.json http://localhost/api/diaries
   ```
2. 用 `--data-urlencode` 把每个字段单独编码（繁琐）
3. 改用 PowerShell 跑 + `Invoke-RestMethod -Body ($body | ConvertTo-Json) -ContentType 'application/json'`

**对比 PowerShell**：PS 自动按 UTF-8 编码 + 解析 JSON，省心得多；缺点是 PS 对单行连字符参数不友好。**养成"写文件再 data-binary"的习惯能避免 80% 的字符编码坑。**

## 25. @WebMvcTest 切片 ≠ 完整安全隔离：`excludeAutoConfiguration` 拦不住 @Component 过滤器（2026-09-09）

**现象**：给 `AuthController` 写 `@WebMvcTest` 切片测试，启动时 `Failed to load ApplicationContext`：
```
UnsatisfiedDependencyException: Error creating bean with name 'jwtAuthenticationFilter':
Unsatisfied dependency expressed through constructor parameter 0: 
No qualifying bean of type 'com.daylog.security.JwtUtils' available
```

**原因**：以为 `@WebMvcTest(controllers = AuthController.class, excludeAutoConfiguration = SecurityAutoConfiguration.class)` 已经把 Security 全链路踢出上下文了——实际上它**只禁用了 Spring Security 的自动配置**，但 `JwtAuthenticationFilter` 是 `OncePerRequestFilter` 的子类、被 `@Component` 标注，会被 WebMvcTest 的"Web 相关组件扫描"规则自动 pickup，于是它要被 Spring 实例化 → 需要 `JwtUtils` 构造函数参数 → 找不到 bean → 启动失败。

**解决**：**显式用 `excludeFilters` 把 `JwtAuthenticationFilter` 和 `TokenBlacklistService` 这两个 @Component 从 WebMvcTest 扫描里排除掉**：
```java
@WebMvcTest(controllers = AuthController.class,
        excludeAutoConfiguration = SecurityAutoConfiguration.class,
        excludeFilters = @ComponentScan.Filter(
                type = FilterType.ASSIGNABLE_TYPE,
                classes = {JwtAuthenticationFilter.class, TokenBlacklistService.class}))
@AutoConfigureMockMvc(addFilters = false)  // 双保险：万一过滤器被注册也不参与
```
三层防御才彻底：
1. `excludeAutoConfiguration` 干掉 Spring Security 自动配置
2. `excludeFilters` 干掉安全相关的 `@Component`（Filter / 黑名单 Service）
3. `@AutoConfigureMockMvc(addFilters = false)` 让 MockMvc 不挂任何过滤器

**教训**：用 `@WebMvcTest` 测 Controller 时，**`excludeAutoConfiguration` 只禁自动配置类，不禁 `@Component` 扫描**。安全/缓存/消息中间件相关的 `@Component` 必须用 `excludeFilters` 或 `@MockBean` 兜住。Spring Boot 3 + Spring Security 6 下"开箱即用"组合的标配。

## 26. MyBatis-Plus LambdaQueryWrapper 触发 `LambdaUtils` 静态缓存（2026-09-09）

**现象**：纯 Mockito 单元测试中，Service 方法里执行 `new LambdaQueryWrapper<Diary>().eq(Diary::getId, 1)`，报：
```
MybatisPlusException: can not find lambda cache for entity [com.daylog.entity.Diary]
```
跑集成测试时没事，只在 `@Mock` mapper 的单元测试里炸。

**原因**：`LambdaQueryWrapper` 构造时会去 `LambdaUtils` 的静态缓存里查 entity → table mapping，这个缓存在 Spring 上下文启动时由 MP 的 `MybatisPlusInterceptor` 注入；纯 Mockito 测试没启动 Spring，缓存是空的 → 找不到。

**解决**（两条路）：
1. **避免在测试路径里构造 lambda wrapper**：让业务代码走 `selectById / selectCount / updateById` 这种 ID-based API（lambda 仅用于"动态条件"场景）
2. **让业务代码早返回**：`saveRelations(tagIds)` 检测 `tagIds.isEmpty()` 时直接 return，不进 wrapper 构造路径

**教训**：MP 的 lambda 风格（`Diary::getId`）是**元数据驱动**的，必须有完整的 MP 启动链路才能用；纯单元测试场景下用 `selectById(id)` 这种字符串 API 是更安全的选择。这也是为什么项目中部分 Service 同时提供 ID-based 和 Lambda 两种重载。

## 27. Mockito `method.invoke(obj, null)` 是模糊调用，必须传 `new Object[]{null}`（2026-09-09）

**现象**：用反射测试私有方法 `countWords(String)`：
```java
Method m = DiaryServiceImpl.class.getDeclaredMethod("countWords", String.class);
m.setAccessible(true);
int result = (int) m.invoke(diaryService, null);  // 输入 null 测试空字符串分支
```
报 `IllegalArgumentException: wrong number of arguments`。

**原因**：`Method.invoke(obj, args...)` 的 `args...` 是可变参数。传单个 `null` 时，反射层分不清是"1 个 null 参数"还是"0 个参数的 null 数组"——按后者处理就"参数数量不匹配"。

**解决**：显式包成数组：
```java
int result = (int) m.invoke(diaryService, new Object[]{null});  // 1 个 null 参数
```

**教训**：反射调用方法时，**所有 null 参数都要用 `new Object[]{null, null, ...}` 包一层**。同理 `Constructor.newInstance(null)` 也是模糊的，要传 `new Object[]{...}`。

## 28. UnnecessaryStubbingException：setUp 里 stub 的方法在某些测试里没用（2026-09-09）

**现象**：测试类 setUp 给所有依赖打了 stub（如 `when(redisTemplate.opsForValue()).thenReturn(valueOps)`），但个别测试只调 `hasKey` 不调 `opsForValue`，跑完报：
```
UnnecessaryStubbingException: Unnecessary stubbings detected in test class
```

**原因**：Mockito 默认 `Strictness.STRICT_STUBS` 严格模式——每个 `when().thenReturn()` 都必须**至少有一个验证调用**，否则报错。这是 Mockito 4+ 默认行为，目的是提醒你"写多了"。

**解决**（两种）：
1. **改 setUp 为 lazy init**：把 stub 移到测试方法里，谁用谁 stub
2. **类级别放宽**：在测试类上加 `@MockitoSettings(strictness = Strictness.LENIENT)`，让所有 stub 都"软"，未使用也不报错（适合"很多测试共用同一批依赖"的场景）

**教训**：严格 stubbing 是好习惯（能发现"测试不该被 mock 的东西被 mock 了"的 bug），但用 @Mock + @InjectMocks 模式时，setUp 里给所有依赖打桩几乎不可避免——这种场景就用 LENIENT 妥协。**生产代码层级的"测试设计问题"用 @MockBean 替代 @Mock 来解决**（@MockBean 不会被严格计数）。

## 29. GlobalExceptionHandler 把 @Valid 校验失败包成 200 + code=400（设计决策，不是 bug，2026-09-09）

**现象**：写 `login_missingFields_returns400` 测试时，期望 `status().isBadRequest()`，实际返回 200 + body `{"code":400, ...}`。

**原因**：项目 `GlobalExceptionHandler` 设计：
```java
@ExceptionHandler(MethodArgumentNotValidException.class)
public Result<Void> handleValidException(...) {
    return Result.fail(ResultCode.BAD_REQUEST, message);  // HTTP 状态码默认 200
}
```
所有业务异常（包括参数校验失败）都统一返回 `{code, message, data}` 格式，HTTP 状态码固定 200，前端按业务码判断错误类型。

**解决（测试侧）**：把期望改成
```java
.andExpect(status().isOk())
.andExpect(jsonPath("$.code").value(400));
```
如果想真返回 HTTP 400，需要改 handler 用 `ResponseEntity.status(HttpStatus.BAD_REQUEST).body(Result.fail(...))`——但这破坏了"统一响应包装"的设计约定，**不推荐改**。

**教训**：写 Controller 测试前先读 `GlobalExceptionHandler`，理解项目的"HTTP 状态码 vs 业务码"约定；不要默认 Spring Boot 标准的"4xx 对应业务错误"。

## 30. surefire 报告被沙箱挡住，但 surefire 实际成功写盘（2026-09-09）

**现象**：跑 `mvn test` 看到完整的测试过程 + surefire 写盘日志，最后一条是 sandbox `SANDBOX PERMISSION DENIED` 报错，但 surefire 实际已经把 `target/surefire-reports/*.xml` 写出来了。

**原因**：surefire 写报告时是 Java 内部 IO，写入 `target/` 完全成功；但 mvn 退出阶段（fork 进程销毁、JVM shutdown hook、Windows Crypto cache 清理）会触发对 `C:\Users\陈福樵\AppData\Roaming\Microsoft\Crypto\RSA\` 的访问，沙箱策略拦了这步。

**解决**：看测试结果不要看 mvn stdout（可能被截断），直接读 `target/surefire-reports/*.txt`（每类一行 `Tests run: N, Failures: 0, ...`）和 `*.xml`（详细结构）。退出码非 0 不一定代表测试失败，要看报告。

**教训**：沙箱环境下跑 mvn，**把"退出码"和"测试结果"分开看**——报告文件才是可信的事实来源。stdout 可能被沙箱在最后阶段截断。

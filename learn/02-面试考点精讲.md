# 面试考点精讲（结合 Daylog 项目）

> 每个考点按"原理 → 项目里怎么用 → 面试怎么答"组织。写代码时对照着看，理解会深一层。

## 考点 1：为什么前后端分离？跨域怎么解决？

**原理**：前端（静态资源）和后端（API 服务）独立开发、独立部署，通过 HTTP + JSON 通信。分离后职责清晰、可独立扩展，但浏览器有同源策略，会产生跨域问题。

**项目里的做法**：
- 开发环境：Vite `server.proxy` 把 `/api/**` 转发到 `localhost:8080` 并去掉 `/api` 前缀。浏览器以为请求的是 5173（同源），实际由 Node 帮你转发——**代理绕过跨域，而不是解决跨域**。
- 生产环境：Nginx 做同样的反向代理，另外后端也配了 CORS 兜底。

**面试话术**："我们在开发环境用 Vite 代理、生产环境用 Nginx 反向代理，让浏览器视角始终同源。同时后端配置了 CORS 允许指定来源，双保险。"

## 考点 2：JWT 认证全流程（本项目核心）

**原理**：JWT = Header.Payload.Signature 三段式。服务端用密钥对前两段签名，客户端每次请求带上 token，服务端只需验签——**无状态，不用像 Session 那样存服务端**。

**项目里的完整链路**：
1. 登录成功 → 用 jjwt 生成 token（载荷放 userId、用户名，有效期 7 天）→ 返回前端
2. 前端存 localStorage，axios 请求拦截器自动加 `Authorization: Bearer <token>`
3. 后端写一个 `JwtAuthenticationFilter` 挂进 Spring Security 过滤器链，每次请求解析 token、验签、查 Redis 黑名单，通过则构造 `Authentication` 放进 `SecurityContextHolder`
4. 登出 → token 写入 Redis 黑名单（`jwt:blacklist:<token>`，TTL = token 剩余有效期）

**JWT 的经典缺陷和我们的应对**（面试官必追问）：
> 问："JWT 不是无状态吗？登出怎么生效？token 被盗怎么办？"
> 答："JWT 天生无法主动失效，这是它对比 Session 的短板。我的方案是引入 Redis 黑名单：登出时把 token 存入黑名单并设置与剩余有效期一致的 TTL。校验时先验签、再查黑名单。这样既保留了 JWT 无状态验签的性能优势，又补上了可控失效的能力。"（这个回答能体现你理解技术权衡，而不是背概念）

## 考点 3：逻辑删除 vs 物理删除（本项目亮点 ★）

**原理**：逻辑删除（`deleted` 标记位）可恢复、保留审计数据，是默认推荐；但它有代价——**逻辑删除的记录仍占据唯一索引的位置**。

**项目里的真实冲突**：diary 表有 `uk(user_id, record_date)` 保证一天一篇。如果用逻辑删除：用户删掉今天的日记（记录还在，只是标记 deleted=1）→ 再写当天日记 → 唯一索引冲突，永远写不了。

**决策**：diary、tag、diary_tag、attachment 用物理删除；只有 user 表用逻辑删除（账号注销是低频操作且无唯一索引冲突）。

**面试话术**："逻辑删除不是银弹，它和唯一索引天然冲突。我的项目里日记表有'一天一篇'的唯一约束，所以日记和标签刻意选了物理删除，只在用户表用逻辑删除。选型要基于具体业务约束，而不是无脑套规范。"

## 考点 4：雪花 ID vs 自增 ID

**项目做法**：所有表主键 BIGINT，MyBatis-Plus `ASSIGN_ID` 应用层生成雪花 ID。

**为什么不用自增**：① 自增 ID 会暴露业务量（看 id 就知道注册了多少用户）；② 分库分表后自增 ID 会重复，雪花 ID（时间戳+机器位+序列号）天然全局唯一。
**代价要知道**：雪花 ID 趋势递增但不连续，页大小比 64 位 int 大，MyBatis-Plus 前端还有 JS 精度问题（见踩坑记录，Long 转字符串返回）。

## 考点 5：Redis 缓存与一致性（本项目核心 ★）

**项目场景**：统计接口（心情曲线、热力图）计算成本高、读多写少，是典型缓存场景。

**方案：Cache-Aside（旁路缓存）+ 主动失效 + TTL 兜底**
1. 读：先查 Redis → 未命中查 MySQL → 结果写入 Redis（TTL 5 分钟）
2. 写：日记增删改后**删除**对应缓存 key（删而不是更新，避免并发写覆盖）
3. TTL 5 分钟是最后兜底：即使主动失效因异常没执行，最多 5 分钟后数据也会自然一致

**面试话术**："我用的 Cache-Aside 模式，写操作后删缓存而非更新缓存，因为并发写时更新缓存容易把旧值写回去。删除后下次读自然回源。极端场景下（删缓存失败）靠 5 分钟 TTL 兜底，最终一致。"

**追问"为什么不用先更新数据库再更新缓存 / 延迟双删？"**：能说出"更新缓存有并发覆盖问题"就及格；延迟双删是知道即可（我们 TTL 方案已够用，方案要与业务规模匹配）。

## 考点 6：并发安全——"一天一篇"怎么保证？

**三层防御**：
1. 前端：编辑页查当天日记，存在则进编辑模式（体验层）
2. 服务层：保存前 `select count` 检查当天是否已有日记（友好提示层）
3. 数据库：`uk(user_id, record_date)` 唯一索引，并发穿透前两层时由 DB 拦截（最终兜底层）

**面试话术**："任何约束我都遵循'前端友好提示 + 服务层校验 + 数据库约束兜底'的三层防御，数据库是最后一道防线，永远不能只依赖代码判断。"

## 考点 7：附件"先上传后关联"设计

**问题**：编辑器里插图时，日记还没保存，diary_id 不存在。
**方案**：图片先上传 → 返回 attachmentId → 日记保存时把 attachmentIds 回填关联 → 定时任务清理 24 小时未关联的孤儿文件。
**面试价值**：体现"边界拆分"思想——上传和业务保存是两个事务边界，解耦后各自可重试、可清理。

## 考点 8：RESTful 设计规范

对照本项目自查：
- ✅ 资源用复数名词：`/diaries`、`/tags`
- ✅ 动作由 HTTP 方法表达：GET 查、POST 建、PUT 改、DELETE 删
- ✅ 分页/过滤走 query 参数：`/diaries?mood=4&page=1`
- ⚠️ 少数动作不好映射 REST（如 `/auth/logout`、`/ai/reports/generate`），业内普遍接受"动词路径"的妥协——面试时能主动说出这个权衡是加分项
- 统一响应 `{code, message, data}`：虽然 HTTP 状态码也能表达错误，但国内前后端协作习惯业务码 + HTTP 都为 200 的方式（我们要能同时讲清楚两种流派）

## 考点 9：MyBatis-Plus 的定位

**一句话**：MP 是 MyBatis 的增强——单表 CRUD 继承 `BaseMapper` 零 SQL（`LambdaQueryWrapper` 类型安全），复杂统计 SQL 依然手写 XML。**不是替代 MyBatis，而是让简单的更简单**。
项目里：日记 CRUD 用 MP；心情趋势、连续天数统计这类 SQL 用 XML 写。

## 考点 10：定时任务的注意点

项目里两个定时任务：AI 周报（周一 08:00）、孤儿文件清理（每日凌晨）。
**要点**：
- `@Scheduled(cron=...)` + `@EnableScheduling`
- 任务要 try-catch 包住单个用户的处理，一个用户失败不能影响整批
- 分布式部署时多实例会重复执行 → 要提一句"生产上可用分布式锁或 xxl-job"（知道即可，项目里单机够用）

## 考点 11：容器化部署（Docker Compose）

**项目里的做法**：四个容器 —— mysql、redis、backend（Spring Boot）、nginx（前端），一条 `docker compose up -d --build` 拉起。

**设计亮点（面试逐条讲）**：
1. **多阶段构建**：`maven 构建` → `JRE 运行` 两个阶段，最终镜像只有运行时依赖，体积小（不含 JDK/Maven/源码）
2. **依赖健康检查**：backend `depends_on: condition: service_healthy`，MySQL/Redis 真正就绪（mysqladmin ping / redis-cli ping）后才启动后端，杜绝启动期连接闪断
3. **配置与代码解耦**：`application-prod.yml` 里所有连接参数 `${DB_HOST:mysql}` 由 compose 注入；密钥走 `.env`（不进镜像、不进 Git）
4. **数据持久化**：命名卷（named volume）挂载 MySQL 数据、Redis AOF、上传目录——容器删了重建数据不丢
5. **schema 自动初始化**：schema.sql 挂到 MySQL 镜像 `/docker-entrypoint-initdb.d/`，首次启动自动建表
6. **JVM 容器友好**：`-XX:MaxRAMPercentage=75` 让 JVM 按容器内存限额自适应堆大小

**常见追问应对**：
> 问："compose 和 k8s 什么关系？"
> 答："compose 是单机多容器编排（开发/小规模），k8s 是集群编排（生产/高可用）。我这个项目规模用 compose 合适，接口层面与容器平台解耦，未来迁移 k8s 只需把每个服务抽象成 Deployment + Service。"

## 考点 12：前端构建产物体积优化思路（简历性能优化点）

**现状**：Element Plus 全量引入 → 主 chunk ~830KB；ECharts 全量 → 统计页 chunk ~1.1MB；md-editor-v3 引入的 CodeMirror 语言包非常多。构建已按路由懒加载分包（页面级 code-split 已生效），但组件库/图表库仍是整包。

**可落地的优化路径（按收益排序）**：
1. **Element Plus 按需引入**：`unplugin-auto-import` + `unplugin-vue-components`，自动只打包用到的组件 → 主包可降 ~60%
2. **ECharts 按需注册**：`echarts/core` + 只 `use` 用到的 Chart/Component/Renderer（LineChart、CalendarChart、PieChart、CanvasRenderer）→ 统计包可降 ~70%
3. **手动分包**：`build.rolldownOptions.output.codeSplitting` 把 element-plus / echarts / md-editor-v3 拆成独立 vendor chunk，充分利用浏览器并行加载 + 长缓存

**面试话术**："路由懒加载已经让首屏只加载登录页代码。下一步组件库按需引入 + ECharts 模块化注册能把首屏体积再砍一半，这是可以量化（gzip 前后对比）写进简历的优化项。"
